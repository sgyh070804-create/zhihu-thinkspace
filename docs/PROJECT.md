# ThinkSpace 项目计划

更新：2026-11-13。当前处于立项阶段，功能尚未实现。后续源码、文档和进度以此仓库为准。

## 定位
AI 阅读思考助手与个人收藏知识库：收藏问答、拓展视角、观点沉淀。

优先使用知乎官方提供的知识库检索与直答能力，把开发重点放在阅读体验、来源引用、观点比较与个人判断的沉淀上，不重复搭建平台已经提供的检索基础设施。

## 产品范围
1. 知乎 OAuth 登录，选择并导入收藏夹内容。
2. 在指定收藏夹内问答，展示原文片段与来源。
3. 拆解帖子主张、论据、隐含前提；对照文章呈现分歧，后续结合知乎和全网检索提供其他解释与反例。
4. 用户确认后保存个人观点、依据和修改历史。

以上为目标范围，不要求同时实现。首个可运行版本只完成演示资料的限定知识库问答与引用，不以 OAuth、收藏同步、观点卡或公开部署为前置条件。

## 核心产品设计：三种思考模式
灵感泡泡、思想分叉、共思群聊是产品的核心差异化方向。收藏问答与检索提供基础能力，围绕用户提出问题、探索联系、检验判断、沉淀观点组织体验。以下均为待实现设计。

### 灵感泡泡：发现问题与联系
- 用户记录一句感受、疑问或猜想；也可从收藏中提取，经用户确认后成为泡泡。
- 思考路径允许停留或回退：触动 → 疑问 → 猜想 → 联系 → 检验 → 暂时判断，不强制完成流程。
- 两个泡泡可通过拖动相碰探索联系；先让用户表达可能的关系，再由 AI 提供有依据的关联、反例或新问题。联系牵强时允许不建立连接。
- 展开泡泡可区分用户原话、收藏依据、AI 推测；新资料可提示与旧问题的关联，由用户决定补充或合并。
- 首版范围：记录念头、选择两个泡泡探索联系、保存一个新问题；暂不建设复杂知识图谱。

### 思想分叉：检验判断成立的条件
- 从一个问题或泡泡进入，用户可先记录直觉，再探索思想实验。
- 每次改变一个关键条件，邀请用户重新判断；在相关位置展示文章主张与原文依据。
- AI 构造的情境必须明确标识，不冒充文章内容；用户可纠正情境与原文的关联。
- 不以改变立场为成功指标，不预设正确答案；允许坚持原判断并补充理由。
- 首版范围：两篇文章、三个情境、一份由用户确认的判断记录，包含适用条件和未解问题。

### 共思群聊：用户与多智能体共同讨论
- 用户参与并控制讨论方向，可点名角色、要求证据、暂停讨论或将一句话保存为泡泡。
- 初始角色：梳理者澄清概念与问题；质疑者检查前提和反例；查证者在授权范围内检索并展示依据。
- 各角色使用独立职责提示、按需裁剪的上下文与工具权限；可共用同一底层模型，不要求部署多个模型。
- 服务端负责发言调度，默认由最相关角色回应，不让所有角色机械轮流发言；设置每轮调用预算、停止条件和用户取消机制。
- 各角色可以修正或保留分歧，不强制达成共识。最终由用户确认自己的暂时判断、依据与疑问。
- 首版范围：一个问题、三个角色、用户可点名的有限轮次讨论；暂不做无人值守的长时间自主辩论。

三种模式共用问题、资料引用和思考记录。泡泡可进入分叉或群聊；群聊中的分歧可进入分叉；模式切换沿用用户确认的记录与授权范围。每次只帮助用户推进一小步，保留用户自己发现联系和形成判断的空间。

## 语气与对话行为设计
语气是核心体验的一部分。先通过提示词、正反对话范例和人工评审校准，不把模型微调作为前置条件。
- 灵感泡泡：轻、短、留白；有启发，但不把偶然联系夸大成深刻洞见。
- 思想分叉：克制地追问条件，不诱导用户接受预设答案，不把转变立场当作胜利。
- 共思群聊：角色体现不同思考职责，不靠固定口头禅塑造人设；允许赞同、修正和暂时不发言。
- 共同要求：自然、具体、不奉承、不说教、不为反对而反对；明确区分引用、推测与用户判断；不机械地每轮追问。
- 同时校准接话时机、发言长度和停止时机，避免长篇讲课及多角色刷屏。

最小评审方式：
- 建立固定对话样本，覆盖模糊念头、不同意见、证据不足、用户纠正、用户想停止等场景。
- 为各模式维护可接受与不可接受的表达示例，并记录提示词版本。
- 人工核对是否帮助用户推进思考、是否尊重其判断、依据是否清楚，以及是否在适当时停止；模型或提示词变更后复核。
- 正确性、范围隔离和引用要求不能为语气效果让步。

## 首版技术路线
- Web：Vue 3、TypeScript、Vite；按需要使用 Element Plus，适配手机。
- 服务端：Python、FastAPI、Pydantic、httpx；统一封装知乎 API，管理凭证、范围校验、错误和引用。
- 检索：优先使用知乎知识库上传与检索 API，由平台承担资料解析和检索。项目仍使用检索增强生成的思路，但首版不自建 RAG 基础设施。
- 生成：优先使用知乎直答 API，将本次检索片段作为上下文传入；先验证 zhida-fast-1p5，按需要比较 zhida-thinking-1p5。
- 数据：首轮使用原创测试文本或获准使用的真实文章及本地映射；需要持久化收藏归属、知识库映射和观点时再引入 PostgreSQL。
- 部署：先本地运行；链路稳定后再选择演示部署方式。Docker Compose、Nginx、SSE 不作为首轮前置条件。

首版不要求本地部署生成模型或嵌入模型，不引入 BGE-M3、Qdrant、BM25、重排模型，也不绑定千问 API。只有官方服务存在经验证的能力缺口时，才针对缺口评估替代服务或自建方案。

## 官方接口与已查阅的文档能力
平台：https://developer.zhihu.com/
赛事：https://www.zhihu.com/hackathon

以下为 2026-11-13 查阅官方文档得到的接口契约，尚未使用本项目凭证完成实测，不代表项目已实现：
- 知识库文件上传：POST /api/v1/knowledge/files。支持 TXT、Markdown、PDF 等文件，可通过 KnowledgeBaseID 指定目标知识库，由平台同步解析并挂载；首次使用需先登录直答知识库完成初始化。
- 知识库检索：POST /api/v1/knowledge/search。支持 Query、KnowledgeBaseIDs、RecallScopes、Limit；返回命中的正文片段 Content、KnowledgeBaseID、DocName，以及可选的 RecallContentID、OriginUrl。
- 直答：POST /v1/chat/completions。文档列出 zhida-fast-1p5、zhida-thinking-1p5、zhida-agent；支持 model、messages、stream。文档明确快速与思考模型支持 role/content 上下文传参。
- 数据接口使用 Access Secret Bearer 鉴权及秒级 X-Request-Timestamp；凭证只放服务端环境变量。

待实测重点：
- 项目账号的模型与知识库权限、额度、延迟和错误处理。
- 指定知识库的检索边界、资料不足行为、上下文约束与回答引用准确性。
- 多用户场景下知识库归属、授权与凭证的对应关系；不能把开发者的默认知识库当作所有用户的共同空间。
- 收藏夹列表与内容接口的鉴权、分页、全文覆盖；收藏夹与直答知识库是否存在直接关联能力。没有确认前，不假设收藏会自动进入知识库。
- 外部搜索、OAuth 及点赞历史按实际需求再核实。

工作台内的开发辅助额度与产品运行所需 API 额度分开核算；未确认可用于 API 调用的额度不计入运行预算。

## 实现约束
- 服务端维护用户、收藏夹、知识库和来源的映射；先校验当前用户归属，再选择允许检索的知识库 ID，不能直接信任前端提交的 ID。
- 限定收藏夹问答只传对应 KnowledgeBaseIDs，不附加扩大范围的 RecallScopes。官方文档规定二者同时传入时取并集，不是交集。
- 返回结果再次核对 KnowledgeBaseID；映射不明或越界时停止回答。平台检索不替代应用自身的权限控制。
- 区分全文、摘要与缺失正文，不将摘要当作全文。
- 收藏不等于认同；分析结果不自动保存为用户观点，个人观点由用户确认。
- 区分收藏、演示资料与外部资料；资料不足时明确说明。引用从实际检索结果和本地来源映射生成，不信任模型编造的来源。
- 密钥、OAuth token、真实用户数据不得提交到 Git；上传超时或结果未知时先核对状态，避免盲目重复上传。

## 按优先级执行的开发路线

### P0：先跑通官方 API 的最短闭环
- [ ] 准备两份观点有差异的原创测试文本或获准使用的真实文章，保存来源并设置固定问题与预期依据；原创样本明确标识，不冒充知乎文章，不提交真实用户私有资料。
- [ ] 优先核对知乎 CLI 并用其完成上传、限定检索与直答验证；仅在需要自动回归或 CLI 缺少必要能力时补充最小脚本，暂不接 OAuth。
- [ ] 使用两个知识库验证限定范围；仅在另一个库出现的信息不能被当前库检索结果带入。
- [ ] 核对正常问题、无相关资料、模型超时、错误凭证和引用对应关系；记录脱敏验证结果及实际额度。
- [ ] 验收：一次运行可完成上传、检索和回答；命中片段及来源可核对；无依据时说明不足；失败有明确错误。若平台存在缺口，先记录具体失败点，再决定是否补充其他服务。

### P1：把已验证链路做成可用页面
- [ ] 建立最小前后端骨架、依赖与 .env.example。
- [ ] 建议边界：web/ 负责交互；api/app/providers/zhihu.py 封装平台请求；api/app/qa.py 编排范围校验、检索、回答与引用；api/fixtures/ 放虚构样本。
- [ ] 提供健康检查、当前用户收藏夹列表、指定收藏夹提问接口；身份从服务端上下文取得。
- [ ] 单页支持选择演示收藏夹、输入问题、查看回答、展开原文片段。
- [ ] 验收：手机宽度可操作；切换收藏夹不会保留或覆盖为旧回答；加载、失败、资料不足均有明确展示；跨用户和跨收藏夹检查通过。固定开发身份仅用于本地验证，公开部署前接入真实身份校验。

### P2：接入真实收藏
- [ ] 根据已实测协议实现必要的 OAuth 与收藏夹选择。
- [ ] 先单次导入一个收藏夹，再增加分页、去重、同步状态与恢复。
- [ ] 持久化用户、收藏夹成员关系、知识库映射和原文来源；如需将内容上传为文件，保留可追溯映射。
- [ ] 验收：重复导入不重复；缺失正文明确标记；不同用户和收藏夹的数据隔离；不假设收藏删除会自动触发知识库删除。

### P3：逐项实现核心思考模式
- [ ] 先完成灵感泡泡最小闭环：记录念头、两泡关联、保存新问题及依据。
- [ ] 实现思想分叉：两篇文章、三个单条件变化情境、用户确认的判断与未解问题。
- [ ] 实现共思群聊：三个职责角色、按需发言、用户点名、轮次预算与停止控制。
- [ ] 建立三种模式共享的思考记录与切换机制，保存用户确认的观点和修改历史。
- [ ] 为各模式编写语气正反例，使用固定样本进行人工评审。
- [ ] 按需接入外部资料，单独标识来源和检索范围。
- [ ] 手机体验完善与演示部署。
- [ ] 验收：分析可追溯到原文；收藏立场与个人观点分开；外部资料不会混入限定收藏夹回答。

每次功能提交同步更新文档，记录改动目的和验证结果。
